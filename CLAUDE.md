# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin ("mod") named `projektfarben`, published through the marketplace `max-mods` defined in this repo (`.claude-plugin/marketplace.json`, manifest and version in `.claude-plugin/plugin.json`). It gives every project a color emoji, puts that emoji in front of each session title in the Claude desktop app's sidebar, draws a colored project band above the prompt, and adds the `/projektfarbe` command. A sleep mode (`/projektfarbe schlaf`) swaps the bright emoji for plain shapes and the band for muted colors.

All user-facing text (command output, band labels, README) is German. Many identifiers and all persistent store keys are German too (`Farbe`, `FARBEN`, `farben`, `gelernt`, `versucht`, `bandAus`, `gesehen`, `stand`). Code comments are English. Keep this split.

## Commands

```bash
claude plugin validate .   # check manifest, marketplace and hooks
claude plugin test .       # run hooks/*.test.tsx
```

There is no `package.json`, build step or linter. The plugin runtime loads the TypeScript/TSX directly; `claude-code` (and `claude-code/testing` in tests) are provided by the runtime, not installed.

## Architecture

- `hooks/hooks.json` lists the module entry, `hooks/register.tsx`, which exports `register` and wires these engine events:
  - `session.start`: registers `/projektfarbe`, then in the background learns existing sidebar colors once, fills the band state, counts the open pull requests and issues, and recolors this session's title.
  - `turn.complete`: only for the session's own turns (`e.agentId === undefined`; subagent turns are skipped). Stores why the turn ended (`e.reason`) under `stand`, refreshes the band (a color may have been picked in another session; the context gauge reads `$.session.usage()`), counts the pull requests and issues again at most every five minutes, and recolors the title. If the app has not named the session yet, it retries once after 20 s via `$.clock.after`.
  - `command.run` for `projektfarbe`: show / set color / `standard` / `alle` / `status` / `band` / `breite` / `schlaf [satz]` / `bunt`.
  - `ui.render` for `AbovePrompt`: the band (color block and name, which open the repository when pressed, `PRs: n` and `Issues: n` with any new ones raised, then the action icons, in this order: the session actions `✦` opinion, the golden teacher (Fable), `↑` review + PR, the handoff, the stack rebuild (only where the folder holds a compose file: `hasStack` in the view, read by `readDienste` through `$.fs.list` and the pure `erkenneDienste`), the check `e2e` and the merge, all of them left of the counts; the context gauge, then at the right edge the overview `☰` and the settings cogwheel `⚙`) and its color picker with the mode switch. Passes through to `next(e)` when there's a survey, no project, or the band is hidden. The layout follows `e.props.bodyColumns` (the cells the band's tree is laid out in, always present): `bandStufe` (colors.ts) picks the roomiest of the one-row layouts in `BAND_FORMEN` and `zwei`. The actions are icons in all of them (a written-out layout was dropped: the hover cards say what an icon does; the keys `meinung` / `fable` / `review` / `handoff` / `stack` / `pruefen` / `merge` / `uebersicht` / `einstellungen`): `icons` (the gauge with its word and the full bar), `kompakt` (no "Kontext" word, a `COMPACT_CELLS` bar), `dicht` (the same, items closer together: `columnGap` 1 and no spacer node), `minimal` (only the percentage, no bar) and `zwei` (two rows, never three: name, counts and short gauge above; below the session actions at the left and the overview and settings at the right, the second row indented under the name; `shortName` / `nameBudget` cut a too long name with "…"). The gauge stays in the first row in every layout. The widths in `bandBreite` are measured on the desktop (proportional font: under one cell per character) and are approximations, tuned in the constants at the top of that block; `/projektfarbe breite` reports `bodyColumns`, the layout drawn last and the cells each one-row layout needs for this content (a plain `lastBand` variable in `register`, since drawing must not write state), or that the band is hidden (`bandAus` is shared by all sessions, and a hidden band is not drawn at all). The one-row layouts are a Box with `justifyContent="space-between"`, `flexWrap="nowrap"` and `overflow="hidden"` and two parts: the project, the session actions and the counts at the left, the gauge with the overview and settings flush right (`SETTING_COUNT` icons; `bandBreite` counts the gaps between these groups). It never wraps: after a resize the surface draws the old tree in the new width until the hook answers, and a wrap then made the band jump to two rows; what does not fit is cut off at the right for that moment. Nothing in the band may break inside itself for the same reason: the gauge's "Kontext" and the percent sign are joined by `NBSP`, or a squeezed row broke "8 %" in two. Adding an action means one entry in `ICON_SVG` (a `viewBox`, an optional `height`) and one in `defs`; the field, the Button and the hover then come from `draw`: each `Svg` is drawn `ICON_BOX * CELL_PX` wide so its viewBox centers the glyph in the field the Button's hover patch covers, and a test holds every entry to a viewBox and a drawing no wider than the field. The icons stand in fields of `ICON_BOX` cells so they are evenly spaced (eight, or nine beside a compose file: `BandInhalt.hasStack` makes `bandBreite` count one more); all actions are drawn as `Svg` (`ICON_SVG`, one family of line icons on a 24 grid, so they share size, weight and color: text glyphs next to them sat lower, smaller and darker; one mid gray `ICON_SVG_COLOR` since an `Svg` is an image and takes no theme color, `ICON_SVG_SIZE` px, each field centering its icon in the row) where the surface has the element, which the terminal's table lacks: there they stay the text glyphs (`✦ ✧ ↑ ✉ ⇉ ☰ ◐ ✕`). A Button takes only strings and `Text` (any other child is refused), so the icon stands in the field and a Button of `ICON_BOX` blanks lies over it in an absolute Box, and the press lands on that Button (the keys stay); each field also holds a hover card (an absolute Box, `display: none`, `hover: { display: 'flex' }`, in a keyed Box) in the band's own row, since the surface clips a card to the band: the left group's cards open to the right of the icon, the right group's to its left, so none reaches past the band's edge. `bandStufe` takes the layout drawn last (`lastBand.stufe`) to hold the band in it until the room for a roomier one is `HYSTERESIS_CELLS` (one) clear: the surface re-draws only once a resize settles, so a window at rest must show the roomiest layout that fits. Widths in `bandBreite` are calibrated on desktop screenshots (the gaps there measure about 22 px for `columnGap` 2 and about 15 px for 1), a test pins the switch points, and `SLACK_CELLS` is the room a row has beyond `bodyColumns`. The widths come in two `Metrics` sets: `DESKTOP` (measured, proportional font) and `TERMINAL` (a character is one cell, a gap is what `columnGap` says, the spacer is its four blanks), picked by `e.surface === 'terminal'`. Only the session's own view (no `agentId`) is remembered in `lastBand` and held in its layout; a project name has its blanks joined by `NBSP`; a missing `bodyColumns` (an older Claude Code) counts as 120.
  - `ui.render` for `Pane` (`requestId` `uebersicht`): the side panel with the overview of all sessions. It is opened by `/projektfarbe übersicht` (also `uebersicht`) and the band's `uebersicht` button via `openPanel` (`$.ui.open`); where that answers `isPlaced: false` the command prints the text of `status` instead. `loadPanel` reads `readUebersicht` into the `uebersicht` atom (while one reading runs, none starts); `refreshPanel` (end of `afterTurn`) reloads the sessions at most once a minute, gh's pull requests at most every five (`prCache`, by `repoKeyOf`; the `aktualisieren` button and the two commands pass `isForced`), and only while the atom's `isOpen` is true (set by `openPanel`, cleared by the `ui.close` hook and the `schliessen` button). The panel has two views in the atom's `ansicht`: `status` (default; `buildBereiche` in colors.ts cuts the overview into sections `dringend` / `dudran` / `review` / `laeuft` / `aufraeumen` by `bereichOf`: a stopped session in work is `dudran`, "your move", this session counts as running; each session two lines with a rail in the section's color, `statusFarbe` coloring the label, the buttons and the summary chips (`uebersichtZaehler`) at the top; the headings carry a fold button `falten-<id>` over the atom's `zu`, `laeuft` folded at first, in the project view `projekt-<name>`) and `projekt` (the groups of `buildUebersicht`; in sleep mode the heading's block already is the mark, so the mark is not repeated in its text), switched by the `ansicht` button. Keys: `aktualisieren`, `ansicht`, `schliessen`, `falten-<id>`, `oeffnen-<sessionId>` (hands the row's `link`, a plain `claude://` address from `list_sessions`, to the system through `$.process.run`: `rundll32 url.dll,FileProtocolHandler`, then `open`, then `xdg-open`; a Link is no option, the desktop draws only `https:` links), `archivieren-<sessionId>` (only where `archiveReason` in colors.ts says so; calls `archive_session` through `callJson`'s server with a `reason`; a refusal or error is a toast, the row stays). `open_session_in` is no option for opening: it only works for `self` and sessions this session started.
  - `ui.render` for `Spinner`: puts the project's mark in front of the spinner's word or message; passes through when the band is hidden.
  - The band's `meinung` action (`✦`) is the independent Opus opinion, asked for in the chat the way the person would prompt it themselves: it fires at once, `bitteSenden` (the one sender of both session actions) sends `meinungPrompt(projekt)` through `$.prompt.submit` with `asUser: true`, a turn of its own once the session is idle. The prompt is the same for every case and states goals, not a form: the session decides from the conversation what is meant (the last question, a plan to rework, the state of the project), starts one `general-purpose` subagent on `model opus` (the Agent tool takes the aliases `sonnet` / `opus` / `haiku` / `fable`, not full model ids: a full id was refused when this ran as a pane) and builds its task itself: the matter itself (question, plan verbatim, the files concerned), not its own conclusion (or the opinion only follows it), nothing it does not need (no conversation history), the rest the subagent reads in the repository itself. It asks for a direct answer with evidence for every claim and says where it disagrees; the session relays the answer unchanged and adds where it differs. No length cap, fixed headings or ban on reading: such gates cost quality, and a test holds the prompt free of them. A refused or failing submission is a toast. There is no pane, state or cost gate: the answer is a chat turn the person sees and can answer. The tests cover the prompt and the submission, not what the model does with it.
  - The band's `fable` action (the golden teacher, `✧` on the terminal) is the one to press when it matters, beside the opinion, which stays the everyday Opus view: `fablePrompt(projekt)` is built like the opinion prompt (the session decides what is meant, hands one `general-purpose` subagent on `model fable` the matter itself and why it matters, never its own conclusion or the conversation, and relays the answer unchanged) and covers a second opinion on a decision that is hard to undo or a plan much depends on, a thorough review of the changes (the branch and its base, the subagent takes the diff itself) and a question the work is stuck on. The subagent goes to the bottom of it, says the decisive thing first and where it is unsure, and changes nothing. Its icon is a figure in a mortarboard, filled in `GOLD` with a `GOLD_DARK` outline and cap, so it stands out from the gray family on purpose.
  - The band's `review` action (`↑`, "Review + PR") is the same kind of prompt: `reviewPrompt(projekt)` has the session check the work (the diff since the base branch, real findings fixed, the project's tests run), commit what belongs together in the style of the last commits, push the branch and open the pull request, then give the link. Pressing the button is the go-ahead for exactly those three steps: the prompt rules out a merge, a push to the base branch and a force push, and has the session stop and say why where a step cannot be done (red tests, nothing to commit, no remote, a finding that needs the person), instead of working around it. Like the opinion prompt it states goals and leaves the how to the session; a test pins the order of the three steps and the limits.
  - The band's `handoff` action (the flying letter) is the same kind of prompt: `handoffPrompt(projekt)` has the session write a message for a fresh session that carries on where this one stands: the goal, what is done and decided (with the reason), what is open and what comes next, where it is risky, and the files, branches or PRs concerned; what the new session reads in the repository itself (code, `git log`, `CLAUDE.md`) stays out, and no conversation history. It is written to be pasted as the first message of a new session; nothing is changed or started. The prompt is a guess at what the button should do (a text to paste, not a session started for the person), and starting the session itself is the next step if that is wanted.
  - The band's `merge` action is the same kind of prompt, for what the person types most often: `mergePrompt(projekt)` has the session merge the open pull requests in a sensible order (the independent ones first, then those that build on them; on green checks only, a clear conflict resolved and the checks run again), then solve the issues that are clear and small enough (or that the new state solves) in a branch and pull request of their own each and merge those too on green checks. Its limits keep one click safe: no force push, no change to the main branch's history, no drafts; what is red, needs a decision or stays unclear is left and named with the reason. Its icon is the merge glyph with a green check (`ICON_SVG_OK`), and the open pull requests stand beside it as small raised digits (`raised(prLabel(openPrs))`, in the field one cell wider, `MERGE_EXTRA`), so it reads as "merge these"; on the terminal the glyph `⇉` and the same digits.
  - The band's `pruefen` action is the same kind of prompt, for checking a change: `pruefenPrompt(projekt)` has the session work in four steps (the project's lint, type check and format over the changed files; tests for the paths of the diff that no test covers, tests that would be red without the change; the real flow in a browser with Playwright, using the project's own skills and scripts first and setting Playwright up minimally, saying what it installed, where it is missing; a read of the Docker stack's containers and logs where one runs). Existing snapshots are reported, not renewed. Its limits: no push, no merge, no test deleted or weakened, production code left alone; a step that cannot be done stops with the reason. Its icon is the word `e2e` itself, drawn narrow and tall so it fits the square, the 2 in the check's green; on the terminal `✓`.
  - The band's `stack` action rebuilds the Docker stack, and exists only where `erkenneDienste` finds a compose file (`docker-compose*.yml`, `compose*.yaml`, with `override` or `dev` in the name) in the session's folder: `stackPrompt(projekt)` has the session first read whether the stack runs against a live account or with a live release (then it stops and asks), then `docker compose -p <name> up -d --build` from the folder, then check health and that the running state is the folder's (git SHA, version or build time). Its limits: no `down -v`, no volume or data deleted, no database reset, nothing outside the stack touched. Its icon is the Docker logo as the original (nine containers and the whale, filled in `DOCKER_BLUE`, with the golden teacher the exception to the gray line family, so `ICON_SVG.stack` carries its own `width` and `height`) with a green circular arrow at the lower right; on the terminal `▣`.
  - The settings cogwheel (`einstellungen`, `⚙`) replaced the separate color and hide icons: it opens the color picker (the colors of the set in the store and the mode switch) and the picker holds an `ausblenden` button that hides the band (`bandAus`).
- `hooks/colors.ts` holds the pure logic with no engine dependency: project detection, color assignment, title planning, store parsing. Put new logic here when it can be tested without the engine. Colors come in sets (`Satz`: `BUNT`, `DAEMMERUNG`) that are plain data; the functions take the set as a last, optional argument (default `BUNT`), and `register.tsx` reads the active one from the store (`satzNow`). A further sleep set is one more `Satz` in `SAETZE` and `SCHLAFSAETZE`, with an `emoji` of its own: the color picker's mode switch (`modusLabel`) lists every set in `SAETZE` by its emoji and name, so a new set shows up there without a UI change.
- `types/index.d.ts` declares the per-session `view` and `uebersicht` atoms' shapes (the contract must be self-contained, so `PanelUebersicht` mirrors `Uebersicht` from colors.ts: change both together) by augmenting `PluginState` in `claude-code`. Change it together with the `view` atom in `register.tsx`.

### Renaming sessions

Titles are changed through the desktop app's own MCP server `ccd_session_mgmt`: `get_session` (with `session_id: 'self'`), `list_sessions` (returns the other sessions), and `set_session_title`. Results come back as JSON in text content blocks (`callJson`). This only works in the desktop app; in a terminal session only the band shows.

The pull request and issue counts and the repository link run the person's own `gh` through `$.process.run` (`gh pr list`, `gh issue list`, `gh repo view --json url` once per folder for `repoUrl`, and `gh pr list --web` / `gh issue list --web` behind the counts), so they need `gh` on the PATH and logged in; when a count cannot be read the band shows a dimmed `?` (so it keeps one shape, and is not mistaken for "none open") and `/projektfarbe` shows why (`prsNote`, `issuesNote`). New entries (a number above the highest in `gesehen`) show as raised digits behind the count (`superscript`); the first reading of a repository only sets the baseline (`markSeen` with `isFirstOnly`), and pressing a count raises it to what is open now. `gesehen` is keyed by the repository folder (`repoKeyOf`); `seenFor` still reads an entry under the project name, where earlier versions kept it, until the folder has its own. With a release build of Bramble (the person's own browser) the name, `PRs:` and `Issues:` open their pages there instead: `findBramble` (register.tsx) looks, on every count and every press, for the newest `target\release\bramble.exe` by modification time in the Bramble repository (`BRAMBLE_REPO`, else `brambleRoot`'s default under `USERPROFILE`) and each of its `.claude\worktrees\*`, and `brambleStart` (colors.ts) starts it through `powershell Start-Process` (`\$.process.run` would wait for the window) with `LWB_URL`, its own profile `LWB_PROFILE=projektfarben` (with the default profile a link would overwrite the person's saved tabs on close) and `LWB_NO_PINS=1`; `LWB_ADBLOCK=off` (`BRAMBLE_ADBLOCK`) starts it without its built-in ad blocker (uBlock Origin Lite), so band links run lean. The view atom carries the build as `bramble`; with one, the name is a Button (key `repo`) beside the plain color block, since a Link is opened by the surface. Without a build: : the desktop draws a Button as its native control and drops the colors and bold inside it; without an address they stay plain text. For the same reason only the words `PRs:` / `Issues:` are Buttons; the bold count and the raised "+x" stand beside them in a keyed Box (`prs-zahl`, `issues-zahl`), and the name carries `color="text"` so the link does not paint it. The block and the gauge are runs of non-breaking spaces on a colored background (`NBSP`), not empty Boxes: on the desktop those sat off the line of the text beside them.

`/projektfarbe status` is split in two so the side panel reuses the data (`uebersichtZaehler` makes its summary chips): `readUebersicht` (register.tsx) asks `get_session`, `list_sessions` (whose rows carry `branch`, `isRunning`, `isArchived`, `lastActivityAt` and sometimes the app's own `prNumber` / `prState`) and, per repository (`repoKeyOf`), all at once, in the folder of one of its sessions, runs two `gh pr list`: `--state open` with `isDraft,reviewDecision,statusCheckRollup` (the costly checks only for the open ones) and `--state all` with `number,state,headRefName` only, joined by `mergePrs`; the pure `statusOf`, `buildUebersicht` and `uebersichtText` (colors.ts) turn that into a status per session, groups and text. `statusOf` orders: running, a merged or closed pull request, an aborted or failed last turn (only while the session is active within three days; after that it rests, with "zuletzt abgebrochen"), an open pull request, in work or resting; a resting status carries `tage`, which `archiveReason` reads. A cancelled check is not a red CI (`CI_ROT`): workflows cancel their older runs on a new push. A session's pull request is the app's `prNumber` / `prState` when the row has one, with `gh`'s entry of that number adding CI, review and draft; without it, the newest `gh` lists for the session's branch. The app does not say whether a session waits for input, so no status covers that.

Engine work in `session.start` and `turn.complete` runs fire-and-forget (`void … .catch(() => undefined)`) so a session or turn never waits on the app, or on the person answering the app's rename prompt.

### Persistent store (`$.store`, shared by all of the person's sessions)

| Key | Content |
|---|---|
| `farben` | project name, lowercased → color emoji (`mark`) of the bright set |
| `farben-daemmerung` | the same for the sleep set `daemmerung` (every set has its own key, `Satz.storeKey`) |
| `modus` | id of the set in use; the bright one `bunt` when absent |
| `gelernt` | `true` once the colors already in the sidebar were learned (`learnPicks`, majority mark per project) |
| `versucht` | session id → the title last tried, capped at 300 entries |
| `bandAus` | `true` when the band is hidden |
| `gesehen` | repository folder (`repoKeyOf`, lowercased, `/`) → `{ pr, issue }`: the highest pull request and issue number the person has seen; entries written before by project name are still read as a fallback (`seenFor`) |
| `stand` | session id → `{ grund, um }`: why the session's last own turn ended (`answer`, `aborted`, `refusal`, `error`) and when (`$.clock.now()`), capped at 300 entries |

These keys hold existing users' data: renaming them or changing their format needs a migration. `versucht` is written *before* `set_session_title`: renaming a title the person set makes the app ask them, and a "no" must not be asked again, even after a restart.

### Rules that span both files

- Project = basename of the session's folder, compared case-insensitively. A path under `.claude/worktrees/` counts as its repository; anything under `scratch-workspaces/` and drive roots have no project.
- A new project gets the first color in its set's `reihenfolge` that no project has yet; with all of the set's colors taken (18, or 10 in sleep mode), a hash of the name decides.
- A title's marks are recognised across all sets (`markOf`, `stripMark` strip every leading mark), so switching sets replaces a mark instead of stacking one. Marks of a `strikt` set are plain text shapes and only count in front of a space or the end, so a title like `▲Plan` is left alone.
- The sleep set uses shapes, not emoji, because a session title is plain text and emoji colors belong to the system: on Windows the moon phases and several nature emoji render vivid. Only the band can carry a muted color. Its hexes stay under 0.06 chroma (OKLCH) and at least 5 apart (OKLab x100); a test holds them to that.
- Placeholder titles (`New session`, `Untitled`, …) mean "not named yet" (`planTitle` → `unnamed`): no rename, retry later.
- Every color has a `name` (ASCII, e.g. `kreis-gruen`), a `mark` (an emoji, or a plain shape in sleep mode) and a `hex` for the band; `findFarbe` maps umlauts and spaces so `grün` and `kreis weiß` work.

## Tests

`hooks/projektfarben.test.tsx` uses `claude-code/testing`. Pure helpers are tested directly. Engine tests drive the real `register` through `$.session.start`, `$.turn.complete`, `$.command.run` and `$.ui.mount`, with:

- `fakeDesktop(self, others, { refuse })` answering `mcp.call` with in-memory titles (`refuse` simulates the person declining a rename);
- `mock.clock(on)` with `clock.settle()` / `clock.advance(ms)` for the background work and the 20 s retry;
- `mock.store(on, initial?)` for the persistent store;
- stubs for `command.register`, `session.start`, `session.cwd` and `turn.complete`.

UI tests find the repository link by its type (`Link`, `href`) and press buttons by their React `key` (`aktualisieren`, `ansicht`, `schliessen`, `falten-<id>`, `oeffnen-<id>`, `archivieren-<id>`, `uebersicht`, `einstellungen`, `meinung`, `fable`, `review`, `handoff`, `stack`, `pruefen`, `merge`, `farbe-<name>`, `abbrechen`, `ausblenden`, `prs`, `issues`, `repo`, `modus-<id>`), so keep those keys stable. Sleep mode is driven through `$.command.run` with `args: 'schlaf'`; the picker's `farbe-<name>` keys then carry the sleep set's names.

## Reviewing the prompts

The band's seven prompt buttons (`meinungPrompt`, `fablePrompt`, `reviewPrompt`, `handoffPrompt`, `mergePrompt`, `pruefenPrompt`, `stackPrompt` in colors.ts) are the part of the mod a reviewer cannot see in a diff of behavior. `/projektfarbe prompts` prints them as one Markdown document (`promptsMarkdown`, with `PROMPT_INFO`: what each button does and what to check), `docs/PROMPTS.md` is that output, and `docs/prompts.html` is a readable page of the same texts. An agent reviewing a change reads `docs/PROMPTS.md` first. The code is the one source: when a prompt or its `PROMPT_INFO` entry changes, regenerate both files (the command's output is the Markdown file; the page is rebuilt from it) so the diff of the docs shows what changed in what the session is asked. A test holds the document to the functions, not the files to the document.

## Previewing a change

Every change that shows in the band or the panels is previewed in a session of its own before it is merged. This is how it is done every time:

1. Commit on the working branch (local only, no push) and raise `version` in `.claude-plugin/plugin.json`: a marketplace update only reinstalls a higher version.
2. Load the branch into the marketplace folder, a clone of this repository at `~/.claude/mods/projektfarben` (the `source` of `max-mods` in `known_marketplaces.json`): `git fetch <this repository's folder> <branch>`, then `git checkout -B vorschau-<name> FETCH_HEAD`. It leaves `main` there until `git checkout main` puts it back, which is done before the merge.
3. `claude plugin marketplace update max-mods`, then `claude plugin update projektfarben@max-mods`. The installed copy lives in `~/.claude/plugins/cache/max-mods/projektfarben/<version>`; a session started after this loads it.
4. Start a session with `start_session` (`user_asked`, `fresh`, `use_worktree: false`, a cheap model, named `vorschau-<n>`) whose brief says what to look at and its only task: answer with the one sentence "Vorschau bereit." and do nothing else (no reading, no commands), so the context gauge shows. The person looks at the band and panels there and reports back.

Only after the person has seen it: PR, merge to `main`, `git checkout main` and `git pull` in the marketplace folder.

When behavior or commands change, update the German README (`Was der Mod macht`, `Befehle`, `Grenzen`).
